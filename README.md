# Отчет

## 1. Воспроизведение результатов

Для автоматизации экспериментов сделаны два скрипта:

- **`setup.sh`** — запускает контейнер c параметрами из тестового задания и устанавливка Clang и Clang Build Analyzer.
- **`run.sh`** — сборка проекта с записью результатов в `results/`.

В репозитории находятся две версии сервиса:

- **`baseline/`** — исходный проект без изменений.
- **`optimized/`** — проект с реализованной оптимизацией.

По умолчанию `run.sh` собирает обе версии. Для запуска конкретной версии можно передать аргумент `baseline` или `optimized`.

```bash
./setup.sh

./run.sh
./run.sh baseline
./run.sh optimized
```

Сборка выполняется в Release с использованием Clang, флага `-ftime-trace` и четырёх параллельных задач (`-j4`). Кэширование компиляции отключено.

## 3. Гипотеза и реализация оптимизации

В исходной версии проекта `main.cpp` подключает заголовочные файлы:

```cpp
#include "hello_grpc.hpp"
#include "hello_postgres.hpp"
#include "hello_mongo.hpp"
```

Они содержат определения классов и подключают дополнительные зависимости userver, PostgreSQL, MongoDB и gRPC. При этом в `main.cpp` они нужны только для регистрации компонент:

```cpp
.Append<myservice::HelloPostgres>()
.Append<myservice::HelloMongo>()
.Append<myservice::HelloGrpc>()
```

Так как `Append<T>()` является шаблонным методом, компилятору нужно определения соответствующих классов, что приводит к обработке их заголовков при компиляции `main.cpp`. 
Тогда будем проверять гипотезу о том, что перенос регистрации обработчиков в соответствующие `.cpp`-файлы позволит исключить тяжёлые зависимости из `main.cpp`, уменьшить затраты frontend и сократить время полной сборки.

Для реализации гипотезы созданы функции-обёртки:

```cpp
RegisterPostgres(component_list);
RegisterMongo(component_list);
RegisterGRPC(component_list);
```

Их объявления вынесены в отдельный заголовочный файл, а реализации размещены в соответствующих `.cpp`-файлах обработчиков. Таким образом, `main.cpp` больше не требуется подключать заголовки `hello_grpc.hpp`, `hello_postgres.hpp` и `hello_mongo.hpp`. Их определения используются непосредственно в тех единицах трансляции, где реализованы обработчики.

## 4. Результаты оптимизации

Для получения результатов оптимизированной версии выполнено 5 сборок сервиса `optimized`.

Получены следующие данные:

| Метрика                  |     1 |     2 |     3 |     4 |     5 |       Avg |
| ------------------------ | ----: | ----: | ----: | ----: | ----: | --------: |
| real                     | 45.45 | 43.29 | 44.33 | 44.29 | 43.56 | **44.18** |
| user                     | 70.97 | 67.99 | 69.61 | 69.15 | 68.43 | **69.23** |
| sys                      |  3.13 |  2.85 |  2.91 |  2.85 |  2.82 |  **2.91** |
| Parsing (frontend)       |  36.4 |  34.6 |  35.4 |  35.1 |  34.9 | **35.28** |
| Codegen & opts (backend) |  10.6 |   9.7 |  10.1 |   9.7 |   9.5 |  **9.92** |

Сравнение результатов :

| Метрика                     | Baseline | Optimized |   Изменение |
| --------------------------- | -------: | --------: | ----------: |
| real (s)                    |    45.65 |     44.18 |  **−3.22%** |
| user (s)                    |    69.11 |     69.23 |  **+0.17%** |
| sys (s)                     |     3.04 |      2.91 |  **−4.08%** |
| Parsing (frontend, s)       |    36.50 |     35.28 |  **−3.34%** |
| Codegen & opts (backend, s) |     8.80 |      9.92 | **+12.73%** |

Также время frontend `main.cpp` снизилось с **4765 до 2631 ms**.  

Среднее реальное время сборки сократилось на **1.47 с**, то есть уменьшилось на **3.22%**.
Суммарное время frontend уменьшилось на **1.22 с (3.34%)**, тогда как время backend увеличилось на **1.12 с (12.73%)**.

## 5. Выводы

Эксперимент показал, что вынос регистрации компонентов из `main.cpp` позволяет уменьшить зависимости этого файла от тяжёлых заголовков. По результатам пяти измерений среднее реальное время сборки сократилось с **45.65 до 44.18 с**, то есть на **3.22%**. Вынос регистрации снизил суммарное время frontend на **3.34%**, но увеличил суммарное время backend на **+12.73%**. Так как большая часть времени сборки уходит на frontend, то получаем ускорение сборки.
